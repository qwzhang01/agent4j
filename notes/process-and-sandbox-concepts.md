## 一、进程是什么

### 1.1 程序 vs 进程

```
程序（program）  = 磁盘上的一个文件，死的东西（比如 /bin/ls、你的 app.jar）
进程（process）  = 程序的一次运行，活的东西
```

同一个程序可以同时运行多次，产生多个进程。打开三个终端各跑一个 `ls`，就是三个进程。

### 1.2 进程的组成

OS 给每个进程发一套"家当"：

```
一个进程 =
  ├── 虚拟地址空间（一块属于它的内存）
  │     ├── 代码段（加载进来的程序指令）
  │     ├── 堆（new 出来的对象）
  │     ├── 栈（方法调用的局部变量）
  │     └── ......
  ├── 文件描述符表（它打开的文件、socket）
  ├── 环境变量
  ├── 一个 PID（进程号）
  └── 状态（运行中/睡眠/僵尸......）
```

关键理解：**这套家当是每进程一份的，不是共享的**。

### 1.3 虚拟内存：硬件级的隔离墙

这是进程概念里最重要的东西。

```
物理内存（真实的 RAM，只有一根）：
┌─────────────────────────────┐
│ OS 内核 │ 进程A │ 进程B │ ... │
└─────────────────────────────┘

但每个进程"看到"的是自己独占一整根内存：

进程 A 的视角：              进程 B 的视角：
0x0000 ┌────────┐          0x0000 ┌────────┐
      │ 我的代码 │                │ 我的代码 │
      │ 我的堆   │                │ 我的堆   │
      │ 我的栈   │                │ 我的栈   │
0xFFFF└────────┘          0xFFFF└────────┘
     （A 看不到 B）             （B 看不到 A）
```

CPU 的 MMU（内存管理单元）负责翻译：进程 A 访问地址 `0x1000` 时，MMU 把它翻译到物理内存的某一段；进程 B 访问同一个 `0x1000`，翻译到**另一段**。

**进程 A 想直接读写进程 B 的内存？做不到。** 它发出的地址永远先经过自己的页表翻译，根本没有指向 B 的映射。越界访问直接触发段错误（Segmentation Fault），CPU 层面拦死。

这就是为什么把不可信代码放到另一个进程里跑，它**弄不坏你进程里的任何对象** -- 不是靠约定，是靠硬件。

### 1.4 进程怎么来的：fork + exec

Unix 世界创建进程的两步（Java 的 `ProcessBuilder.start()` 底层就是这两个系统调用）：

```
父进程
  ├── fork()  -> 复制出一个子进程（几乎一模一样的副本）
  │               此时子进程还是父进程代码的副本
  └── exec()  -> 子进程把自己的代码段替换成新程序
                  "灵魂换人，躯壳（PID、部分资源）不变"
                  从此子进程跑的就是全新的代码
```

Java 里一行 `pb.start()` = fork + exec。

### 1.5 进程 vs 线程（对比着理解）

```
线程：同一进程内的多条执行流
  -> 共享同一个地址空间（堆、静态变量大家都能碰）
  -> 一个线程把堆写坏，全进程遭殃

进程：独立的地址空间
  -> 堆完全隔离，谁也碰不到谁
  -> 一个进程崩溃，另一个进程照常活着
```

这就是为什么"沙箱"用多进程而不是多线程 -- 线程隔离不住任何东西。

## 二、进程边界给了你什么

把不可信代码放进子进程，进程边界免费送你三样东西：

### 2.1 故障隔离

```
子进程跑 LLM 写的代码：
  -> 抛异常？死在子进程里
  -> System.exit()？退出的是子进程
  -> 堆溢出？溢的是子进程的堆
  -> 死循环？卡的不是你

父进程（你的 Agent 主程序）毫发无伤，继续运行。
```

### 2.2 生命周期控制

父进程对子进程有生杀大权：

```
wait()/waitFor()  -> 等它跑完，拿退出码
destroy()          -> 发 TERM 信号，请求退出
destroyForcibly()  -> 发 KILL 信号，强制击杀（死循环专用）
```

这就是 `ProcessSandbox` 里超时 kill 的基础 -- **进程是 OS 调度的独立单位，所以 OS 能替你单杀它**。线程做不到这一点：线程不能被单独安全 kill，杀线程会留下一堆损坏的锁和状态。

### 2.3 资源统计

进程是资源核算单位：它用了多少 CPU、多少内存、打开了哪些文件，OS 全记账。可以对单个进程设限额（后面讲）。

## 三、关键认知：进程隔离 ≠ 安全隔离

这是理解"进程级沙箱"最重要的一步。

### 3.1 裸进程是"默认开放"的

子进程虽然碰不到你的内存，**但它作为一个正常的 OS 进程，拥有当前用户的一切系统调用能力**：

```
子进程默认能：
  ✅ 读写你用户能访问的所有文件（~/.ssh、项目源码、配置文件）
  ✅ 联网（curl 任何地址、外传数据）
  ✅ 再起它自己的子进程（孙进程）
  ✅ 杀掉同用户的其他进程
  ✅ 把 CPU/内存/磁盘吃满
```

所以裸的进程隔离只解决"**它崩了不连累你**"（故障隔离），不解决"**它作恶怎么办**"（安全隔离）。

```
裸子进程：
  崩溃隔离  ✅
  内存隔离  ✅（虚拟内存）
  文件隔离  ❌
  网络隔离  ❌
  资源限制  ❌
```

### 3.2 进程级沙箱 = 进程边界 + 附加限制

"进程级沙箱"的准确定义：

> **以进程为隔离单元，再在 OS 层面给这个进程的系统能力加限制，使它只能做被允许的事。**

加限制的手段（按 Linux 演进史）：

| 机制 | 原理 | 限制什么 |
|------|------|---------|
| `chroot` | 改变进程看到的根目录 | 文件系统视图（老的，可逃逸） |
| `setrlimit` / `ulimit` | 资源配额 | CPU 时间、内存、文件数、进程数 |
| **seccomp-bpf** | 过滤系统调用 | 白名单 syscall（比如禁 `open`、禁 `socket`） |
| **namespaces** (mnt/net/pid...) | 进程看到独立的 文件系统挂载/网络栈/进程表 | 容器的基础（Docker = namespaces + cgroups） |
| **cgroups** | 资源分组限额 | CPU、内存、IO 带宽 |
| **Landlock** | 进程**自己**先装上 LSM 规则再 exec，规则跨 exec 继承给所有后代 | 文件读写路径白名单（无需特权，dsh 用的） |
| macOS **Seatbelt** | `sandbox-exec` 描述文件，默认允许 + deny 写 + 写白名单 | 文件效果 |
| Windows **受限令牌/ACL** | 降权令牌 + 访问控制条目 | 文件写权限（天然 partial） |

对照 dsh 的后端矩阵，现在能看懂它为什么是这几个了：

```
dsh 的选择 = "限制同内核、同文件系统的子进程"的各平台最优解：

Linux  bwrap     = mnt namespace + pid namespace（用户态，无需 root）
Linux  Landlock  = 先限己再 exec 的启动器（约 300 行 C，无需特权）
macOS  Seatbelt  = sandbox-exec（Apple 已弃用但仍提供）
Win    ACL       = 受限令牌 + 确定性/随机 SID
```

它们全是"给进程加减法"的不同实现，共同点：**限制发生在系统调用那一层** -- 进程伸手去 `open("/etc/passwd")` 的瞬间被内核拦下，返回 `EACCES`。

### 3.3 和我们两种实现的层次对照

```
隔离层级（从弱到强）：

1. 进程内 ClassLoader 隔离（我们的方案2）
     拦的位置：类加载（JVM 层）
     "File 这个类根本加载不进来"
     逃逸：反射 / JNI / 直接走本地调用

2. 裸子进程（我们 ProcessSandbox 的基础）
     拦的位置：内存（硬件 MMU）
     "代码跑在别的地址空间里，崩了不连累我"
     逃逸：子进程有完整系统调用能力，能读文件能联网

3. 子进程 + 限制（dsh 的做法）
     拦的位置：系统调用（内核层）
     "open/socket 那一下就被内核拒绝"
     逃逸：取决于机制（旧 Landlock ABI partial、Win ACL 有硬链接缺口）

4. 容器（namespace + cgroups）
     拦的位置：内核对象视图
     "进程根本看不到外面的文件系统和网络栈"

5. 虚拟机 / microVM
     拦的位置：硬件虚拟化
     "另一个内核"
```

dsh 把 3 留在 `ctx.sandbox` 这个 seam 里，把 4/5 定义为"替换整条能力"的兄弟实现 -- 因为 4/5 不再与宿主共享文件系统和内核，语义上已经不是"包装一下 argv"能覆盖的了。

## 四、一张总图

```
                        谁被隔离？
  ┌──────────────────────────────────────────────┐
  │ 进程内存隔离（MMU 硬件保证，天生就有）           │
  │  子进程崩溃 / 超时被 kill / 吃内存 ──不影响──> 父进程 │
  │                                              │
  │ 然后"进程级沙箱"= 在此之上加闸门：              │
  │                                              │
  │  子进程 ──系统调用──> ┌─────┐                 │
  │   open("/etc/x") --> │内核闸 │ seccomp/Landlock/│
  │   socket(...)    --> │     │  Seatbelt/ACL    │
  │   fork()         --> │     │  <--- 白名单之外   │
  │                      └─────┘      全部拒绝     │
  │                                              │
  │  通过的调用才真正到达：                          │
  │   文件系统 / 网络栈 / CPU / 内存                │
  └──────────────────────────────────────────────┘
```

## 五、回到我们的代码

现在再看 `ProcessSandbox` 就透明了 -- 它用了进程边界的哪些部分：

```
ProcessSandbox（我们的方案1）用了：
  ✅ fork+exec          （pb.start()）
  ✅ 工作目录限制        （pb.directory(sandboxDir)）-- 最原始的文件隔离
  ✅ 环境变量控制        （pb.environment()）        -- 不泄露主进程环境
  ✅ 超时强杀           （waitFor + destroyForcibly）
  ✅ stdout/stderr 捕获 （getInputStream，管道 IPC）

没用到的（所以隔离是"裸进程"级别）：
  ❌ 系统调用过滤        （seccomp -- 需要 C 代码或工具）
  ❌ 文件路径白名单      （Landlock / Seatbelt -- dsh 做的就是这个）
  ❌ 资源配额            （cgroups / rlimit）
```

也就是说：我们的 `ProcessSandbox` = 故障隔离 + 最小便利限制；dsh 的 sandbox-local = 故障隔离 + **内核级文件效果限制**。差距就在那道"系统调用闸门"上 -- 而那道闸门在 Java 里没法纯实现（要碰内核接口），所以 dsh 才专门写了 300 行 C 的 `landlock-run` 原生启动器。这也解释了为什么这条路线到容器之前，业界方案几乎都要带一个原生组件。

---

## 六、一句话总结

> **进程 = OS 里资源分配和隔离的基本单位，靠硬件虚拟内存做到"你崩你的、我活我的"。进程级沙箱 = 把不可信代码关进子进程（拿故障隔离和 kill 权）之后，再用内核机制（Landlock/Seatbelt/seccomp/namespace）把它的系统调用关进笼子（文件、网络、资源限制）。裸进程只防崩溃不防作恶，加了内核闸门才是沙箱。**
