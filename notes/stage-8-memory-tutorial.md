# 第 0 层：为什么需要记忆系统

忘掉所有术语。想象你在用一个 AI 助手，看三个“翻车现场”。

## 翻车现场 1：记不住（跨会话）

```text
你：我对花生过敏，帮我记住。
助手：好的，我已经记住了。
（第二天，新开对话）
你：帮我订个午餐。
助手：好的！为您推荐宫保鸡丁--花生满满，很香哦！
你：？？？
```

**为什么翻车**：大多数 Agent 的“记忆”就是本次对话的消息列表。新开对话，消息列表清空--昨天的“花生过敏”随着上次对话结束就消失了。

**用户感受**：它每次都像第一次见我。

## 翻车现场 2：装不下（对话太长）

```text
第 1 轮：描述问题
第 2-20 轮：各种尝试、报错、日志
第 21-49 轮：缩小范围，锁定方向
第 50 轮：你：所以按我们刚才的分析，下一步该查什么？
助手：（开始胡言乱语，忘记前面分析过的结论）
```

**为什么翻车**：模型一次能读的内容有物理上限（上下文窗口）。对话越长，塞回的历史越多：超限报错；没超限但很长->费用暴涨+注意力稀释（lost in the middle）。

**用户感受**：聊得越久它越笨，而且越聊越贵。

## 翻车现场 3：管不了（记忆出错）

```text
你：（口误）我对花生过敏。
助手：（记住了）
（此后每次推荐食谱都避开花生）
你：其实我说错了，我不过敏。
助手：（新记忆写进去，但旧记忆还在）
（之后行为随机：有时避开花生，有时不避）
```

多人场景更可怕：

```text
同事 A：（说错）数据库密码每周三轮换
Agent：（记住了）
同事 B/C/D：（未来 3 个月，每次问密码都被告知"每周三轮换"）
3 个月后才发现错了 -> 已误导全团队 3 个月
```

**为什么翻车**：记住的只是文字，没有配套管理：不知道谁写的、错了怎么改、过时了怎么清。

**用户感受**：它记错的东西比它忘掉的东西更可怕--因为你会信任它。

## 三个翻车，三个问题

| 翻车 | 问题 | 一句话 |
|------|------|--------|
| 现场 1 | 记不住 | 会话结束，消息列表清零 |
| 现场 2 | 装不下 | 历史全量塞回，有上限、贵、笨 |
| 现场 3 | 管不了 | 光存文字不行，要能溯源/更正/过期 |

## 共同根源

三个问题指向同一个根源：

> **模型是“金鱼”--每次调用都是一张白纸，只认识你这次塞给它的内容。**

记忆系统就是围绕这条金鱼搭建的“外部设备”：把重要的存到窗外（解决记不住），把塞回去的裁剪到装得下（解决装不下），把存的管理起来（解决管不了）。

## 对照我们自己

Stage 1-7 的 Agent 真长这样：

```text
AgentState.messages   ← 全部"记忆"
   run 结束 -> 丢弃          （翻车 1）
buildRequest 全量塞回      （翻车 2）
消息只是文字，无元数据      （翻车 3）
```

Stage 8 的 agent-memory 模块就是逐个堵这三个洞。第 3~7 层会一一对应。

# 第 1 层：两个基石概念

## 概念一：上下文窗口（context window）

### 模型的工作方式

模型不是流式“听”你说话。每次调用：

```text
你发起一次调用：
   把【所有内容】一次性发给模型
        ↓
   模型读完这一坨，生成回复
        ↓
   调用结束。模型对这次调用的记忆【立即清零】
```

三条关键认知：

1. **一次性**：读的是这次塞给它的完整内容，不是边听边想
2. **无后台**：这次没塞的信息，对模型等于不存在（它不会“去查”、“去回忆”）
3. **即焚**：回复完就失忆，下次调用又是一张白纸

那个“一次能塞多大”的物理上限，就是**上下文窗口**。

### 窗口里装什么

```text
┌─────────────── 上下文窗口（比如 128K token）───────────────┐
│ system prompt（人设和规则）                                   │
│ 工具清单（有哪些工具可调）                                     │
│ 历史消息（这个对话之前说过什么）          ← 会话越长这里越胖   │
│ 注入的外部内容（搜到的资料、取回的记忆）   ← 后面几层的主角   │
│ 你刚说的话                                                    │
└────────────────────────────────────────────────────────────┘
```

### token：窗口的计量单位

- 1 个英文单词 ≈ 1.3 个 token
- 1 个汉字 ≈ 0.6~1 个 token
- 粗算：4 个字符 ≈ 1 个 token

最后这条就是 `ContextBudget` 里 `chars / 4` 的依据--估算不需要精确，只需知道“快满了没”。

## 为什么窗口是“稀缺”资源

上限大（128K 听起来很多），但有三重稀缺：

### 稀缺 1：物理上限（硬的）

超限直接报错，没有商量。

### 稀缺 2：钱（每轮重复计费）

```text
第 1 轮：发送 1K token     付费 1K
第 2 轮：发送 1K + 1K      付费 2K
...
第 50 轮：付费 ≈ 50K
50 轮总付费 ≈ 1+2+...+50 ≈ 1275K   ← 平方级增长
```

### 稀缺 3：注意力（越长越笨）

lost in the middle：塞 100 轮历史，模型对开头第 3 轮的约束经常视而不见。**窗口大了 ≠ 窗口好用了。**

> 三重稀缺合起来：窗口不仅要“塞得下”，还要“塞得少而准”。

## 概念二：窗外（与“搬运”）

窗外 = 这次调用没被塞进窗口的所有信息：

```text
        ┌────────────┐
        │  上下文窗口  │ ← 模型唯一能看到的世界
        └────────────┘
              ↑ ↓ 只有两条路
┌─────────────────────────────┐
│           窗外               │
│  · 昨天的对话（已结束）        │
│  · 用户的档案、偏好           │
│  · 上上周的任务记录           │
│  · 公司知识库 / 文档          │
└─────────────────────────────┘
```

记忆系统的本质定义：

> **记忆系统 = 一套在“窗内”和“窗外”之间搬运信息的机制。**

搬运只有两个方向：

```text
写入（窗内 -> 窗外）：这次对话里出现了重要的东西，挑出来存好
读取（窗外 -> 窗内）：下次需要时，把它取回来拼进窗口
```

行业黑话对照：

| 黑话 | 白话 |
|------|------|
| 注入（inject） | 把窗外取回的内容拼进这次的请求里 |
| 召回（recall） | 读取方向的主力动作 |
| 提取（extract） | 写入方向“挑出重要东西”的动作 |

## 用代码印证

```text
"一次性装窗"   ->  ReActAgentLoop.buildRequest()   每步循环都重新装一次窗
"窗内清单"     ->  AgentState.getMessages()        这次 run 的窗口内容
"搬运调度员"   ->  ContextBuilder                   装窗前先做裁剪/注入的扩展点
"计量"         ->  ContextBudget.estimate()        chars/4 估算窗口占用
```

`ReActAgentLoop.buildRequest()` 就是“装窗”这个动作本身：

```text
115:120:agent-core/.../ReActAgentLoop.java
    // Stage 8: use ContextBuilder if configured, otherwise passthrough (backward compatible)
    List<ChatMessage> messages = config.getContextBuilder() != null
            ? config.getContextBuilder().build(config, state)
            : new ArrayList<>(state.getMessages());
```

没配 ContextBuilder = 原样全量装窗（Stage 1-7 行为）；配了 = 装窗前先经“搬运调度员”处理。

## 本层收束

> **模型是一条只有窗口那么大记忆的金鱼；记忆系统就是围绕这条金鱼干活的搬运工--把重要的搬出去存好，把需要的搬进来，顺手把窗口收拾得又小又准。**

所有主流方案本质都是这个搬运工，差别只在三件事：**搬什么、怎么搬、何时搬**。这三件事就是第 2 层的三问框架。

# 第 2 层：三问框架（总纲）

任何记忆方案都只是对同样三个问题的不同回答。学会用这三问去拆，就不会迷路。

```text
             ┌─────────────────────────────────────┐
             │           窗外（记忆库）              │
             └─────────────────────────────────────┘
                ↑ 问1        ↓ 问2          问3
             存什么？      怎么取？       怎么忘？
             （写入）      （读取）      （遗忘/治理）
                │              │              │
             挑重要的      需要时搬回     过时的、错的
             搬出去        窗内           清理掉/管起来
```

三问顺序 = 一条信息的生命周期：**进来（存）-> 被用（取）-> 退出（忘）**。

## 问 1：存什么？（写入）

四件事要拍板：

**a. 存原材料，还是存提炼物？**

```text
方案 A：把原始聊天记录整段存      （存录像）
方案 B：从对话提炼出一条条事实存  （存要点）
```

A 忠实但臃肿，检索时要再加工，没法直接管理；B 有损但干净，天生适合检索、去重、更新。主流选 B（我们也是：`MemoryEntry` 不存原始 `ChatMessage`）。

**b. 谁来判断“重要”？** 三种流派：

| 流派 | 谁判断 | 例子 |
|------|--------|------|
| 规则 | 关键词/格式命中 | 我们 v1 的偏好关键词表 |
| 模型判 | LLM 读对话后决定 | mem0 的提取管线 |
| 显式 | 用户/模型主动说“记住这个” | ChatGPT memory、我们的 save_memory |

**c. 什么时候写？** 每轮写 / 会话结束写 / 模型随时调工具写。

**d. 写之前查不查旧账？** 新事实和已有记忆矛盾怎么办--直接并存会导致行为随机。要做**冲突消解**（mem0 用 LLM 决策 ADD/UPDATE/DELETE/NOOP，我们用 subject 键比对 + supersede）。

## 问 2：怎么取？（读取）

三件事要拍板：

**a. 怎么知道“需要”？** 匹配手段三档进化：

```text
第 1 档：关键词匹配     内容含"过敏"就召回          （我们 v1）
第 2 档：向量相似       语义接近就召回              （Stage 15 RAG）
第 3 档：知识图谱       顺着关系推理召回            （v2 候选）
```

**b. 谁来发起取？** 双通道：

```text
被动通道：每轮自动把相关记忆拼进窗口（模型无感知，保鲜）
主动通道：给模型一个 search 工具，它觉得需要就自己查（灵活省空间）
```

成熟系统两条都要（P7）。

**c. 取回来放哪、放多少？** 记忆注入要吃窗口预算--注入 2K 记忆，可能就要先压缩掉 2K 旧历史。

## 问 3：怎么忘？（遗忘与治理）

两个层次：

**a. 正常遗忘**（信息过时）：

| 方式 | 机制 | 例子 |
|------|------|------|
| TTL 过期 | 写时定好有效期，到期自动失效 | “促销到周五” |
| 新旧取代 | 新事实进来，旧的标记退役 | “过敏”->“不过敏” |
| 窗口滑出 | 只保留最近 K 条 | 滑动窗口 |
| 人工删除 | 用户/管理员手动清 | GDPR |

**b. 治理**（记忆出错/被滥用）：

```text
溯源：谁写的？什么时候？从哪次对话来的？   （provenance）
更正：错了怎么改？直接删=销毁证据，正确做法是标记取代、留痕
权限：谁能读/写/删？个人记忆和共享记忆规则一样吗？
```

> 不对称原则：**忘掉一条正确记忆，损失是一条信息；留着一条错误记忆，污染的是之后每一次回答。** 治理严格程度随共享范围升级。

## 实战：用三问拆解两个主流方案

**mem0**：

```text
存什么：会话结束 -> LLM 提炼事实 -> 与旧记忆比对 -> ADD/UPDATE/DELETE/NOOP
怎么取：向量化 -> 语义相似检索 -> 每轮注入
怎么忘：UPDATE/DELETE 由 LLM 决策 + 用户管理
```

**ChatGPT memory**：

```text
存什么：双通道--模型自动存的 saved memories + 历史对话语义引用
怎么取：saved memories 每轮全量注入 + 历史按语义检索
怎么忘：用户在设置里逐条可见、可删
```

## 我们的系统对三问的回答（预告）

| 三问 | 我们的回答 | 详细在哪层 |
|------|-----------|-----------|
| 存什么 | 规则提取 + 三道闸（阈值/频控/冲突取代）+ 显式 save_memory | 第 5 层 |
| 怎么取 | scope+关键词检索 + 被动注入 + 主动 search 工具；超预算先压缩 | 第 4、5 层 |
| 怎么忘 | TTL 惰性过期 + supersede 留痕取代 + MemoryAdmin 治理 | 第 6 层 |
| （升维） | 多人共享：scope 隔离 + 待审后生效 | 第 7 层 |

# 第 3 层：分层模型（把三问安放到时间尺度上）

## 一个常见的错误：把所有记忆塞进一个列表

```text
一个 ArrayList 存所有记忆：
  - 今天的对话消息
  - 上周的对话消息
  - 用户偏好（"喜欢深色模式"）
  - 任务工作状态（"正在等 CI 通过"）
  - 公司知识库摘要
全混在一起，统一存取
```

为什么不行？生命周期完全不同：

```text
今天的对话消息    活几小时
上周的对话消息    活几天
用户偏好          活几个月甚至永久
任务工作状态      活几分钟到几天
公司知识库        永久，更新慢
```

混在一起的两类灾难：

```text
灾难 A（过度保留）：今天的临时消息被当成永久记忆，半年后还在污染检索结果
灾难 B（误清永久）：清理过期任务状态时，顺手把用户偏好也清了
```

**分层不是为了好看，是因为生命周期不同的东西硬塞一起必然互相伤害。**

## 三横：按生命周期分层

人脑参照系（Atkinson-Shiffrin 模型）：

```text
感觉记忆 -> 短期记忆（工作记忆） -> 长期记忆
   不到1秒      几分钟              几天~永久
```

Agent 照搬，三层：

```text
┌─────────────────────────────────────────────────────────┐
│ 第 1 层：Working Memory（工作记忆）                      │
│   = 一次 Agent run 内的消息列表                           │
│   生命周期：一个 run（几十秒到几分钟）                     │
│   存什么：当前这次推理的对话                              │
│   怎么取：不需要取，它本来就在窗内                        │
│   怎么忘：run 结束自动消失                                │
├─────────────────────────────────────────────────────────┤
│ 第 2 层：Session Memory（会话记忆）                      │
│   = 一次会话的多轮消息累积                                 │
│   生命周期：一次会话（几小时到几天）                       │
│   存什么：这个会话从开头到现在的所有消息                   │
│   怎么取：每轮 run 开始时，拼进工作记忆                    │
│   怎么忘：会话结束归档或丢弃                               │
├─────────────────────────────────────────────────────────┤
│ 第 3 层：Long-term Memory（长期记忆）                    │
│   = 跨会话持久化的事实条目                                 │
│   生命周期：跨会话、跨 run，长期持久                       │
│   存什么：提炼后的 MemoryEntry（不存原始消息）             │
│   怎么取：按需检索注入                                    │
│   怎么忘：TTL 过期 / supersede 取代 / 管理员删除           │
└─────────────────────────────────────────────────────────┘
```

### 三层之间的关系

```text
       用户消息
          ↓
    ┌─────────────┐
    │ Working Mem │ ← run 内活跃
    │ (AgentState)│
    └─────┬───────┘
          │ run 结束同步回
          ↓
    ┌─────────────┐
    │ Session Mem │ ← 会话内累积
    │ (ChatSession)│
    └─────┬───────┘
          │ 会话结束提取
          ↓
    ┌─────────────┐
    │ Long-term   │ ← 跨会话持久
    │ (MemoryStore)│
    └─────────────┘
          ↑
          │ 下次会话开始时检索注入
          └────── 回到 Working Mem
```

## 关键认知：为什么 long-term 不存原始消息

```text
错误做法：long-term 存原始 ChatMessage
  - 半年后：5 万条消息，90% 是废话
  - 检索时：命中一堆无关历史，浪费预算
  - 管理时：没法改、没法溯源

正确做法：long-term 存提炼后的 MemoryEntry
  - "用户：我对花生过敏" -> 提炼成 [事实] 用户对花生过敏
  - 半年后：几百条干净事实，每条有 subject/type/provenance/status
  - 检索精准、好排序、可管理
```

> **原始消息的归原始消息（会话日志/checkpoint），长期记忆的归长期记忆（提炼条目）。**

## 对应到我们的代码

```text
第 1 层 Working   ->  agent-core 的 AgentState.messages
                      - mutable，run 内随时改
                      - Stage 6 的 Checkpoint 存的就是它

第 2 层 Session   ->  agent-memory 的 ChatSession.history
                      - 会话内累积，剔掉 system prompt
                      - toAgentState() 拼回 working / syncFrom() 从 working 同步

第 3 层 Long-term ->  agent-memory 的 MemoryStore
                      - 存 MemoryEntry（不存 ChatMessage）
                      - InMemoryMemoryStore（v1）/ 后续可换 DB
```

`ChatSession.toAgentState` / `syncFrom` 就是第 1、2 层之间的双向搬运：

```text
toAgentState(systemPrompt)：第 2 层降维成第 1 层（拼 system + 灌 history）
syncFrom(state)：第 1 层同步回第 2 层（剔 system 拉回 history）
```

# 第 4 层：单会话内的问题--上下文管理（compaction）

## 问题重现：长对话的死亡螺旋

```text
第 1 轮：装窗 1K token
第 10 轮：装窗 10K token
第 50 轮：装窗 50K token  ← 三重稀缺全中
   - 物理上限：可能超窗报错
   - 钱：平方级计费
   - 注意力：lost in the middle
```

## 三种解法

| 解法 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| 滑动窗口 | 只保留最近 K 条，老的直接丢 | 简单 | 丢得太狠 |
| 摘要替换 | 老消息总结成摘要替换原文 | 保留要点 | 丢了原文 |
| **压缩+归档** | 老消息总结成摘要 + 原文归档 + 保留最近 K 条 | 要点留窗内、原文可回溯 | 实现稍复杂 |

我们抄的 pi 的 compaction 是第三种。**光“丢”不行，光“摘要”也不行，“摘要+归档”才是闭环**。

## 压缩的完整流程

入口：`ContextCompressor.compress()`，每轮 `buildRequest` 时被调。

### 第 1 步：估预算

```text
ContextBudget.estimate(messages) = 所有消息字符数 / 4
> budgetTokens ?
   否 -> 原样返回，不动   ← 大多数轮次走这条
   是 -> 进入压缩
```

为什么 `chars / 4` 粗糙估算？目标是“压缩先于超窗”，不需要精确。

### 第 2 步：切分消息

```text
所有消息
  ├── system 消息      -> 全部保留（人设/规则不能动）
  └── 非 system 消息
        ├── 前 (n - keepRecent) 条  -> 待归档段（要被压缩的）
        └── 后 keepRecent 条        -> 近期保留段（原样留窗内）
```

`keepRecent` 默认 2~6。最近几轮是模型当前推理最依赖的上下文，不能压。

### 第 3 步：调模型总结

```text
待归档段 -> 拼成长文本 -> 调 ModelClient.chat -> 拿到摘要
```

**失败怎么办？** 降级截断（前 500 字符），不抛异常。**记忆系统的故障不应该拖垮主流程**。

### 第 4 步：重组窗口

```text
压缩后的窗口 = [system..., summary(作为 user 消息), 最近 K 条]
```

摘要伪装成 user 消息，内容前缀 `[Summary of earlier conversation]`。

### 第 5 步：归档原文（关键！）

```text
被压缩掉的原文
  -> 拼成一段文本
  -> 存成 MemoryEntry(type=SUMMARY, scope="session:s1", provenance=MODEL_DERIVED)
  -> 落进 MemoryStore
```

摘要有损，归档兜底回溯。

## 关键设计：就地改写 state

```text
state.getMessages().clear();
state.getMessages().addAll(压缩结果);
```

为什么直接改 state？**因为 Checkpoint 存的就是 state**。

如果只改请求副本不改 state：

```text
压缩时：请求里是[摘要+最近K条]，但 state 里还是[全部50条]
Checkpoint 存的是 state -> 存了 50 条
下次恢复：读回 50 条 -> 又超窗 -> 又压缩 -> 又只改请求...
       永远原地打转
```

**就地改写 = 让 Checkpoint 存的 = 模型实际见过的**。有损的代价用归档补回，形成闭环。

## 真实示例（CompressionExample 输出）

```text
输入：19 条消息，548 token，预算 50 token
   ↓ 压缩
输出：6 条消息，133 token

窗口结构：
  [SYSTEM] You are a debugging assistant.
  [USER]   [Summary of earlier conversation]
           User was debugging an MCP connection issue, tried solutions A and B...
  [USER]   I tried solution 8 but got error code 800...
  [ASSISTANT] Let me analyze solution 8...
  [USER]   So what should I try next?
  [ASSISTANT] Based on the errors, let's check the port configuration.

归档：1 条 SUMMARY MemoryEntry 存进 store
```

## 三问框架回扣

| 三问 | compaction 的回答 |
|------|------------------|
| 存什么 | 被压缩掉的原文 -> SUMMARY 条目归档进 MemoryStore |
| 怎么取 | 摘要留窗内供模型用；原文需要时从 store 捞 |
| 怎么忘 | 窗内的老消息被摘要替换；归档不删（可回溯） |

**compaction 本质是一种“受控遗忘”**：从工作记忆遗忘（腾空间），但归档到长期记忆（保可回溯）。

# 第 5 层：跨会话的长期记忆（提取/检索/注入）

## 问题重现

```text
会话 A（第一天）
  run1：用户说"我对花生过敏"
  会话结束 -> AgentState 丢弃
  ↓
会话 B（第二天）
  run1：用户说"帮我订午餐"
  AgentState 是全新的 -> 模型不知道花生过敏
```

需要两段管道：

```text
写入管道（会话 A 结束时）：从对话挑出"花生过敏"，存进 MemoryStore
读取管道（会话 B 开始时）：从 MemoryStore 把"花生过敏"捞回，注入窗口
```

## 写入管道：四步走

入口：`MemoryExtractor.extractAndStore()`

### 第 1 步：提取候选

```text
输入：本次会话的所有消息
过滤：只看 USER 消息（assistant 回复不值得记，可能含幻觉）
匹配：内容里有没有"偏好关键词"
   - 中文：记住 / 我是 / 我喜欢 / 我不喜欢 / 我偏好 / 我习惯 / 我对...
   - 英文：always / never / prefer / i am / i like...
命中 -> 生成候选 MemoryEntry
   type = PREFERENCE, importance = 0.7, subject = 内容前 20 字
```

### 第 2 步：闸门 1--重要性阈值

```text
candidate.importance (0.7) >= 阈值 (0.5) ?
   否 -> 丢弃
   是 -> 进入下一闸
```

### 第 3 步：闸门 2--频控（去重）

```text
已有相同 subject 且 content 完全相同 ?
   是 -> 丢弃（重复了）
   否 -> 进入下一闸
```

### 第 4 步：闸门 3--冲突取代（supersede）

```text
已有相同 subject 但 content 不同 ?
   是 -> 旧条目 update 为 SUPERSEDED（不物理删！）
        新条目写入 ACTIVE
   否 -> 直接写 ACTIVE
```

矛盾记忆不能并存，否则模型行为随机。

### 状态默认值（第 7 层伏笔）

```text
scope 以 "channel:" 开头 ?
  是 -> status = PENDING_REVIEW（未审不生效）
  否 -> status = ACTIVE（立即可用）
```

### 写入流水线全貌

```text
会话消息
  ↓ 提取（只看 USER + 关键词命中）
候选 MemoryEntry (importance=0.7)
  ↓ 闸1：importance >= 0.5 ?
  ↓ 闸2：同 subject 同内容已存在 ?
  ↓ 闸3：同 subject 异内容 -> 旧的 SUPERSEDED
  ↓ 状态默认值（channel -> PENDING_REVIEW）
store.write(entry)
```

**四步全在写路径**--写谨慎。

## 读取管道：三步走

入口：`MemoryContextBuilder.build()`，每轮 `buildRequest` 时被调。

### 第 1 步：检索

```text
retriever.recall(scopes=[user:u1, channel:c1])
  -> store.query(MemoryQuery)
     - scope 交集过滤（隔离的实现点！scope 不在列表里绝不返回）
     - 只回 ACTIVE
     - TTL 惰性过滤
     - keyword 匹配（v1）
     - 按 createdAt 倒序 + limit
```

**隔离实现位置**：不是 retriever 做，是 store.query 强制。靠机制不靠自觉。

### 第 2 步：渲染

```text
命中的 MemoryEntry 列表
  -> 拼成：
     "[Known memories]
      - [PREFERENCE] 记住我对花生过敏: 记住我对花生过敏"
  -> 包装成一条 user 消息
```

### 第 3 步：注入

```text
窗口 = [system, [Known memories], 历史消息..., 用户刚说的话]
```

注入位置：system 之后、历史之前。

### 关键：注入不落盘

```text
[Known memories] 这条消息【没有】加进 AgentState！
```

为什么？如果注入的记忆被存回 AgentState，下次 extractAndStore 会从 messages 里再提取出这条 -> 写回 store -> **自我复制** -> 记忆库被污染。

**注入是只读搬运**：每轮重新检索、重新注入、用完即弃。store 是唯一信息源。

## 端到端：两次会话串起来（MemoryExample）

### 会话 A（第一天）

```text
用户：记住我喜欢深色模式
  ↓ 提取（命中"我喜欢"）
  ↓ 三道闸全过
store.write(ACTIVE)

Assistant：好的，我记住了。
  ↓ 会话 A 结束
```

store 里现在有 1 条 ACTIVE 记忆。

### 会话 B（第二天）

```text
用户：帮我设置界面
  ↓ MemoryContextBuilder.build()
  ↓ retriever.recall([user:u1])
  ↓ 命中："记住我喜欢深色模式"
  ↓ 渲染 + 注入
窗口 = [system, [Known memories]: - 记住我喜欢深色模式, 帮我设置界面]
  ↓ 发给模型
模型：(看到记忆) -> "好的，帮您开启深色模式"
```

**第 1 轮说的偏好，第 2 天被注入第 2 轮的窗口**。翻车现场 1 修好了。

## 三问框架回扣

| 三问 | 第 5 层的回答 |
|------|--------------|
| 存什么 | 规则提取 USER 消息偏好 -> 候选 -> 三道闸 -> 落库 |
| 怎么取 | scope 内检索 ACTIVE + 渲染注入 + 不落盘 |
| 怎么忘 | TTL 惰性过期 + supersede 取代（第 6 层详讲） |

# 第 6 层：治理--记忆出错了怎么办

## 问题重现：错误记忆的放大效应

```text
用户：（口误）我对花生过敏。
Agent：（记住了）
此后 3 个月每次推荐食谱都避开花生。
用户：其实我说错了，我不过敏。
Agent：（新记忆写进去，但旧记忆还在）
之后行为随机：有时避开花生，有时不避。
```

## 核心不对称：遗忘 vs 治理

```text
遗忘（信息过时了）：
  - 损失：丢一条信息
  - 代价：可接受（用户重说一遍就行）

治理（记忆出错了/被滥用了）：
  - 损失：错误信息被反复放大，污染每一次回答
  - 代价：不可接受（信任被破坏，且很难发现错了）
```

> **忘掉一条正确记忆，损失是一条信息；留着一条错误记忆，污染的是之后每一次回答。**

治理严格程度随共享范围升级--一个人用可以宽松，一群人共享必须先审后用（第 7 层）。

## 治理三件套

### 工具 1：溯源（provenance）--这条记忆哪来的？

每条 MemoryEntry 带 `MemoryProvenance` 四元组：

```text
sourceType  怎么来的
  - USER_SAID     用户在对话里说的
  - TOOL_RESULT   从工具执行结果提取的
  - MODEL_DERIVED 模型总结/压缩/主动存的
  - ADMIN_EDIT    管理员手写或修改的

actor       谁说的 / 哪个工具 / 哪个模型
runId       从哪次 run 提取的（管理员手写的为 null）
at          什么时候记录的
```

四个排查场景：

```text
场景 A："这条记忆对不对？"      -> 看 sourceType
场景 B："谁说的这条？"          -> 看 actor
场景 C："哪次对话产生的？"      -> 看 runId
场景 D："这条是 3 个月前记的"    -> 看 at
```

**provenance 是治理的地基**。没有它，四个问题全部答不上来。

### 工具 2：supersede--错了怎么改？（关键机制）

最直觉的改法“删旧写新”为什么不行：

```text
1. 销毁证据：3 个月后想查"为什么一直推荐错" -> 旧记忆已删，查不到
2. 无法回滚：万一"不过敏"才是错的 -> 旧的已删，回不去
3. 审计断裂：合规要求可追溯 -> 删了就断了
```

正确做法 **supersede（标记取代）**：

```text
旧记忆："对花生过敏" -> status 从 ACTIVE 改为 SUPERSEDED（不物理删！）
新记忆："不过敏"     -> status = ACTIVE, provenance 标记谁更正的

结果：
  - 检索只回 ACTIVE -> 模型只见"不过敏"（行为正确）
  - listByScope 回所有状态 -> 管理员可见完整历史（可审计）
  - 需要回滚？把旧的改回 ACTIVE、新的标 REJECTED 即可
```

**supersede 的本质是“软删除 + 留痕”**。物理删除（`store.delete`）只在 GDPR 场景才用。

### 工具 3：TTL--过时了怎么自动失效？

有些记忆天然有保质期。TTL 机制：写入时设 `expireAt`，查询时惰性过滤。

```text
查询时（store.query 内部）：
  entry.expireAt != null && now >= expireAt ?
    是 -> 跳过（不返回）
    否 -> 正常返回
```

为什么“惰性过滤”而不是“主动清理”？零额外组件（不需要后台线程/锁），代价是过期条目仍占内存（但不影响正确性）。清理任务可后补。

**TTL 的核心不是“怎么删”，而是“怎么让它不再生效”--失效比删除重要。**

## 治理面板：MemoryAdmin

```text
listByScope(scope)    看所有记忆（含所有状态）
listPending(scope)    看待审记忆
approve(entryId)      批准待审 -> ACTIVE
reject(entryId)       拒绝待审 -> REJECTED
updateContent(...)    改内容（provenance 改成 ADMIN_EDIT）
supersede(...)        取代旧条目（旧 SUPERSEDED + 新 ACTIVE）
addEntry(...)         管理员直接写
setTtl(...)           设过期时间
delete(id)            硬删（GDPR 专用，治理别用）
```

**设计原则**：治理操作都走 update（改状态/内容），不走 delete。

## 完整治理场景

```text
T1  用户口误："我对花生过敏"
    -> store: [ACTIVE] 对花生过敏 (USER_SAID, userA, r1)

T2  3 个月内每次推荐食谱都避开花生

T3  用户发现："其实我说错了"
    -> admin.supersede(entryId, "用户不对花生过敏（之前口误）")
    -> store: [SUPERSEDED] 对花生过敏   (USER_SAID, userA, T1)
              [ACTIVE]     不过敏        (ADMIN_EDIT, admin, T3)

T4  之后检索只回 ACTIVE -> 行为正确

T5  半年后审计："为什么前 3 个月推荐都避开花生？"
    -> admin.listByScope 可见完整链：
       T1 用户口误 -> T3 管理员更正。责任清晰、可复盘。
```

## 三问框架回扣

| 三问 | 第 6 层的回答 |
|------|-------------|
| 存什么 | （第 5 层）+ 写入时必须带 provenance 四元组 |
| 怎么取 | （第 5 层）+ 查询时 TTL 惰性过滤 |
| 怎么忘 | **supersede 留痕取代 + TTL 惰性过期 + admin 审核拒绝** |

**治理本质是给“怎么忘”加上了“怎么管”**。

# 第 7 层：多人共享一个 Agent 的记忆

## 问题重现：从个人助手到团队 Agent

```text
频道 c1（团队成员 A/B/C/D 共享一个 Agent）
  - A 说"我们的发布流程是：先过 code review 再合并"
  - Agent 应该记住，之后 B/C/D 问发布流程时都能答
  - 这是"团队公共知识"，不属于任何个人
```

三个新问题：

```text
问题 1：A 的个人隐私怎么保护？
  -> 需要：个人记忆和频道记忆分开存

问题 2：A 说错了怎么办？
  -> 需要：共享记忆写入后不能立刻生效，要先审

问题 3：B 怎么看到 A 留下的团队知识？
  -> 需要：频道记忆对频道内所有人可见
```

三个问题指向同一个解：**scope 机制 + 待审闸门**。

## 核心概念：scope 统一隔离与共享

### scope 就是一个字符串

```text
agent:weather-bot    Agent 自己的常识
user:u1              u1 的个人记忆（只对 u1 可见）
session:s1           会话级事实
task:r42             任务工作记忆
channel:c1           频道共享记忆（频道内所有人可见）
```

### 隔离与共享是同一个机制的两面（哲学 P5）

```text
隔离（user:u1）：
  B 的查询列表 = [user:u2, channel:c1]
  store.query 绝不返回 user:u1 的条目
  -> A 的个人隐私 B 看不到 ✅

共享（channel:c1）：
  A 的查询列表 = [user:u1, channel:c1]
  B 的查询列表 = [user:u2, channel:c1]
  两人都把 channel:c1 放进查询列表
  -> 频道记忆两人都能看到 ✅
```

**ChannelMemory 不是一套新系统**。它就是 `scope=channel:c1` 的一批 MemoryEntry，查询时把 `channel:c1` 放进 scopes 列表就能看到。隔离和共享的差别，仅仅是**scope 在不在你的查询列表里**。

### 隔离的实现位置：store 强制，不靠自觉

```text
store.query(MemoryQuery) 内部：
  entries.stream()
    .filter(e -> query.scopes().contains(e.scope()))   ← 这一行就是隔离的全部
    .filter(e -> e.status() == ACTIVE)
    ...
```

调用方传 `[user:u2]`，store 绝不返回 `user:u1` 的条目。**靠机制不靠自觉**。

## 待审闸门：为什么共享记忆要先审后用

### 个人 vs 共享的风险不对称

```text
个人记忆写错了：
  - 只影响自己
  - 损失：一人一次回答偏了
  -> 可以宽松：写完就 ACTIVE

共享记忆写错了：
  - 影响频道内所有人
  - 被反复检索、反复放大
  - 可能几个月才发现
  -> 必须严格：先审后用
```

### 待审机制完整流程

```text
T1  A 说"密码每周三轮换"
    -> scope=channel:c1 -> status=PENDING_REVIEW
    -> store: [PENDING_REVIEW] 密码每周三轮换

T2  B 检索 channel:c1
    -> store.query 只回 ACTIVE
    -> B 看不到这条 ✅ 防污染

T3  管理员审核：
    -> 正确 -> admin.approve(id) -> ACTIVE
    -> 错误 -> admin.reject(id) -> REJECTED

T4  审核后：
    -> 正确：B 能看到了 ✅
    -> 错误：B 永远看不到 ✅（错误被挡在门外）
```

**待审闸门的本质**：在“写入”和“生效”之间插入人工审核--写入可以自动，但生效必须人工确认。

## 完整场景（ChannelMemoryExample）

```text
T1  用户 A（在频道 c1）：记住我对花生过敏
    -> store: [PENDING_REVIEW] 记住我对花生过敏 (USER_SAID, userA)

T2  用户 B 检索 -> 看不到（PENDING_REVIEW 被过滤）

T3  admin.approve -> status=ACTIVE

T4  用户 B 检索 -> 看到了 ✅

T5  发现记错了，admin.supersede
    -> [SUPERSEDED] 记住我对花生过敏 (USER_SAID, userA)
    -> [ACTIVE]     user A is NOT allergic (ADMIN_EDIT, admin)

T6  审计：admin.listByScope 可见完整链
    -> 谁说的、谁审的、谁改的，全链可追溯
```

## 三个问题全部解决

| 问题 | 解法 | 机制 |
|------|------|------|
| A 的隐私 | 个人记忆 scope=user:u1，B 查询列表不含它 | scope 隔离 |
| A 说错了 | 频道记忆写入默认 PENDING_REVIEW | 待审闸 + supersede |
| B 看到团队知识 | 频道记忆 scope=channel:c1，B 查询列表含它 | scope 共享 |

**三个问题，一个 scope 机制全解**。不需要两套系统。

## 与前几层的回扣

### 第 5 层伏笔回收

第 5 层写入最后一步“channel -> PENDING_REVIEW”揭晓：**共享记忆影响范围大，必须先审后用；个人记忆影响范围小，写完即生效**。

### 第 6 层治理升级

```text
个人记忆治理：supersede + provenance + TTL（事后治理）
共享记忆治理：待审闸（事前治理）+ supersede + provenance + TTL（事后治理）
             ↑ 多了这道事前闸
```

**个人记忆可以“先写后治”，共享记忆必须“先审后用”**。治理时机的前移。

# 第 8 层：进阶视野（选学）

## 话题一：向量检索--我们现在为什么不用

### 第 5 层检索的硬伤

```text
硬伤 1：字面匹配，不懂语义
  存了"我对花生禁忌"，查"过敏" -> 查不到
硬伤 2：查不准也查不全
  存了"用户不喜欢坚果类"，查"花生" -> 查不到
```

### 向量检索怎么解决

```text
步骤 1：向量化（embedding）
  "我对花生过敏"      -> [0.12, -0.34, 0.56, ...]
  "花生是我的饮食禁忌" -> [0.11, -0.32, 0.55, ...]  (很接近)
  "今天天气不错"      -> [0.87, 0.21, -0.09, ...]  (完全不同)

步骤 2：存进向量库（每条 MemoryEntry 多存 vector 字段）

步骤 3：检索时
  查询"过敏相关" -> 也变成向量 -> 找距离最近的条目
  -> "过敏"和"禁忌"都能被找到
```

### 我们 v1 为什么不用

```text
理由 1：教学型要可测--关键词 deterministic，向量每次可能微抖动
理由 2：依赖重--需要 embedding 模型 + 向量库（FAISS/Milvus/pgvector）
理由 3：接口已留好--query(MemoryQuery) 抽象，v2 换向量不动调用方
```

第三条关键：**架构没把检索方式焊死**。v1 关键词、v2 向量、v3 图谱，调用方都不动。这是 Stage 15（RAG）的事。

## 话题二：RAG 与 Memory 的边界

```text
RAG（Retrieval-Augmented Generation）
  检索的是：外部世界知识（文档库 / 知识库 / 网页）
  例子："公司报销政策是什么？" -> 检索报销制度文档
  回答："世界上存在什么"
  比方：查百科全书（客观知识，谁查都一样）

Memory
  检索的是：Agent / 用户的过去（之前的对话 / 提取的事实 / 偏好）
  例子："帮我订午餐" -> 检索"用户对花生过敏"
  回答："我们之间发生过什么"
  比方：翻日记本（私人记忆，因人而异）
```

| 维度 | RAG | Memory |
|------|-----|--------|
| 检索内容 | 文档 chunks | MemoryEntry |
| 隔离需求 | 弱 | 强（个人记忆严格隔离） |
| 治理需求 | 弱（文档错了改文档） | 强（要溯源/更正/待审） |
| 时效性 | 低（文档更新慢） | 高（用户刚说的下一轮就要用） |
| 写入方式 | 离线灌库 | 运行时实时提取 |

**MemoryStore 和未来的 RAG 文档库是两套东西，不混做。**

## 面试终极速答

> 我们的记忆系统按三问框架设计：**存什么**--规则提取 USER 消息偏好，过三道闸（重要性阈值+频控+冲突取代）落库为结构化 MemoryEntry；**怎么取**--scope 内检索 ACTIVE 记忆，渲染成 `[Known memories]` 注入 system 之后，超预算时先 pi 式 compaction 压缩；**怎么忘**--TTL 惰性过期 + supersede 留痕取代 + MemoryAdmin 治理面板。多人共享场景下，channel scope 写入默认 PENDING_REVIEW 先审后用，隔离与共享统一为 MemoryScope 查询列表机制。v1 用关键词检索不用向量（接口已抽象，Stage 15 换实现不动调用方）。

## 附录：各层检验题答案汇总

### 第 1 层
1. 为什么窗口大不等于可以不用记忆系统？三重稀缺：物理上限（多轮总会超）、钱（平方级计费）、注意力（lost in the middle，越长越笨）。
2. 两个搬运方向：写入（窗内->窗外，挑重要的存）、读取（窗外->窗内，需要时取回注入）。

### 第 2 层
1. mem0 选“存提炼物”（LLM 抽取事实存结构化条目），全量存记录选“存原材料”（原始 ChatMessage）。前者干净可管理，后者臃肿难检索。
2. 单人遗忘损失一条信息，可重说；多人共享的错误记忆被所有人反复放大，几个月才发现，污染每一次回答--从“遗忘问题”升级成“治理问题”，需要溯源/留痕/审核。

### 第 3 层
1. 灾难 A（过度保留）：临时消息被当永久记忆，半年后污染检索。灾难 B（误清永久）：清过期任务状态时顺手清了用户偏好。混存导致生命周期不同的东西互相伤害。
2. toAgentState 把第 2 层降维成第 1 层（拼 system + 灌 history 进 AgentState）；syncFrom 把第 1 层同步回第 2 层（剔 system 拉回 history）。两个方向对应 run 开始和 run 结束的搬运。

### 第 4 层
1. Checkpoint 存的就是 state。只改请求副本不改 state -> Checkpoint 存了旧的大列表 -> 恢复时又读回旧列表 -> 又超窗 -> 又压缩 -> 死循环。就地改写让持久化的 = 模型见过的。
2. 降级截断（前 500 字符），不抛异常。记忆系统故障不能拖垮主流程--Agent 不能因为“记不住”就罢工。

### 第 5 层
1. 只提取 USER 消息，因为记忆的本质是“关于用户/世界的事实”，assistant 回复是推理产物，可能含幻觉--记下来等于把幻觉固化。
2. 注入的 `[Known memories]` 不能存回 state，否则下次 extractAndStore 会从 messages 里再提取出这条 -> 写回 store -> 自我复制 -> 记忆库被注入产物污染。

### 第 6 层
1. supersede 不删旧条目的理由：①销毁证据，无法复盘“为什么曾推荐错”；②无法回滚（万一更正才是错的）；③审计断裂，合规要求可追溯。
2. provenance 四元组：sourceType 答“怎么来的/可信度”、actor 答“谁说的/去问谁确认”、runId 答“哪次对话产生的/怎么翻完整上下文”、at 答“什么时候记的/是否过时”。

### 第 7 层
1. B 的检索传 scopes=[user:u2, channel:c1]，不含 user:u1。store.query 里 `.filter(e -> query.scopes().contains(e.scope()))` 把 user:u1 过滤掉。不靠权限不靠角色，就靠“scope 在不在查询列表里”。
2. 不对称原则：个人记忆写错只影响自己（先写后治），共享记忆写错被全团队反复放大（先审后用）。影响范围越大，治理时机越前移。channel 默认 PENDING_REVIEW，user 默认 ACTIVE。

### 第 8 层
（选学层，无检验题）
