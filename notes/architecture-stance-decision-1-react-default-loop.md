# 决策 1：ReAct 作为默认 Loop，而不是 Plan-Execute / Tree-of-Thought

> 对应《agent4j 架构立场》骨架的决策 1。
> 一句话：**默认 ReAct（内层自由探索）+ 显式 Workflow 图（外层结构），按任务层级分，而不是三选一。**

## 一、三个候选方案

### ReAct（Reasoning + Acting，推理与行动交错）

```text
每步：看当前状态 → 决定"调工具"还是"给最终答案"
调工具 → 把观察结果喂回去 → 再看 → 再决定
```

核心特征：下一步由模型根据上一步结果临时决定，没有预先锁定的计划。

### Plan-Execute（计划-执行）

```text
先让 LLM 生成完整计划：step1 → step2 → step3 → ...
然后按计划顺序执行
```

核心特征：路线先定死，执行阶段不再重新规划。

变体：

- **ReWOO**（Reasoning WithOut Observation）：执行时不把每步观察全塞回上下文，省 token。
- **Plan-and-Solve**：先解构问题再分步解。

### Tree-of-Thought（思维树）

```text
每一步生成多个候选思路/动作
评估每条分支 → 选好的继续 → 可回溯换路
```

核心特征：这是搜索，不是顺序执行。像下棋的蒙特卡洛树搜索，不是一条道走到黑。

## 二、为什么默认 ReAct

1. **最通用**：大多数真实 Agent 任务是"边做边看"，结果出来才知道下一步。Plan-Execute 假设结构可预测，ToT 假设需要多路探索——两者都对任务形态有前提，ReAct 没有。
2. **成本最低**：一步一次调用。Plan-Execute 多一次规划且可能白做；ToT 是分支数 × 深度，指数级。
3. **原生匹配 Function Calling**：LLM API 的"模型输出 tool call → 执行 → 喂结果"协议本身就是 ReAct 的形状。
4. **应变强**：每步都能根据新观察改方向。Plan-Execute 的计划一旦错或环境变了，后面全错。

## 三、ReAct 的代价（必须答）

1. **无全局视野 → 会漂移**：没有计划，模型可能跑偏、重复、死循环。`maxSteps` 只是安全阀，不是质量阀——能防止无限跑，不能防止跑错方向。
2. **长任务退化**：跑 20 步后，上下文堆积 + 目标被稀释，模型容易忘了最初要干嘛。
3. **不可并行、不可回溯**：步骤串行依赖；第 3 步走错了，只能从错误状态继续往前走。ToT 能回溯，ReAct 不能。
4. **token 持续膨胀**：每步都追加消息；ReAct 没有"计划"这个可复用锚点，全靠历史堆。

## 四、什么场景会改（边界条件）

### 换 Plan-Execute 的触发条件

- 任务结构已知且稳定（固定多步流程，每步目标明确）。
- 危险操作需要先把计划给人审批再执行。
- 长流水线且 token 敏感 → 用 ReWOO。

### 换 Tree-of-Thought 的触发条件

- 核心瓶颈是"搜索正确推理路径"，不是"编排工具"（数学证明、复杂逻辑、代码+测试验证）。
- 有一个便宜的 verifier 能评判分支好坏——没有 verifier 的 ToT 是纯烧钱。

关键判断句：**ToT 适合"哪条路对"，ReAct 适合"下一步干嘛"。**

## 五、架构师级洞察：不是三选一，是分层

三个方案回答的问题根本不同：

```text
ReAct          → 回答"下一步做什么"（局部决策，内层）
Plan/Workflow  → 回答"整体路线是什么"（全局结构，外层）
ToT            → 回答"哪条推理路径对"（搜索验证，专项）
```

agent4j 的实际做法是这个分层：

```text
内层：ReActAgentLoop（AgentLoop 接口，默认实现，可换）
外层：agent-workflow 的图（7 种节点 + GraphRuntime = 显式的 Plan/图编排）
```

所以真实答案是：**内层 ReAct + 外层显式图。**

- 单次自由探索的任务 → 直接用内层 ReAct。
- 多步、有分支、有人工审批、要并行的流程 → 用外层 Workflow 图，Agent 作为图上的一个节点。

换 Loop 只需提供新的 `AgentLoop` 实现，框架不动——因为 `AgentLoop` 是接口，`ReActAgentLoop` 只是默认实现。

## 六、面试表述

> 默认用 ReAct，因为它最通用、成本最低、原生匹配 function calling，能边做边应变。
> 代价是无全局计划，会漂移、长任务退化、不可回溯，maxSteps 只是安全阀不是质量阀。
> 当任务结构稳定或需要先审计划时，我在外层用显式 Workflow 图，而不是改内层 Loop；
> 当核心是搜索正确推理路径、且有便宜 verifier 时，才考虑 ToT。
> 所以我的架构是内层 ReAct + 外层图，按任务层级分，而不是三选一。

## 关联

- 证据：`AgentLoop` 接口 + `ReActAgentLoop` 实现 + `SimpleAgent` 委托；`agent-workflow` 的 7 节点 + `GraphRuntime` 作为外层显式结构；`maxSteps` 作为安全边界。
- 决策 0「Loop 是函数，不是线程」是内层 Loop 的形态；本决策是内层 Loop 的策略。
