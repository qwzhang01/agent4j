# 知识图谱 vs 图数据库：形态与介质的区分

> 对应阶段：Stage 8 - Memory、Context 与共享记忆治理
> 定位：概念澄清笔记 -- 知识图谱是"存什么形态"，图数据库是"放哪里"，两者正交
> 配套：存储方案选型见 [stage-8-memory-storage-backends.md](stage-8-memory-storage-backends.md)，概念详解见 [stage-8-memory-explained.md](stage-8-memory-explained.md)

---

## 0. 一句话结论

> **知识图谱是一种"数据组织方式"（存什么形态），图数据库是一种"存储介质"（放哪里）。知识图谱可以存在图数据库里，也可以不存在。**

用前述的两个维度拆就清晰：

```text
维度 1：存什么形态
  知识图谱 = 一种形态（节点 + 边，有向图）

维度 2：放哪里
  图数据库 = 一种介质（Neo4j / Graphiti）
```

知识图谱落在维度 1，图数据库落在维度 2。它们是正交的。

---

## 1. 知识图谱（形态）

知识图谱的核心是**用图的方式组织知识**：实体是节点，关系是边。

```text
(用户A) --[对花生过敏]--> (花生)
(用户A) --[亲属]--> (用户B)
(用户B) --[对坚果过敏]--> (坚果)
(花生) --[属于]--> (坚果类)
```

这是"怎么组织数据"的问题，跟"存在哪"无关。

---

## 2. 图数据库（介质）

图数据库是**专门存图结构、做图查询的存储引擎**：Neo4j、Graphiti、Amazon Neptune。它原生存节点和边，查询用 Cypher 这种图遍历语言。

---

## 3. 知识图谱不一定存在图数据库里

这是最容易混的点。知识图谱可以存在很多种介质里：

| 介质 | 怎么存知识图谱 | 怎么查 | 代表 |
|------|-------------|--------|------|
| **图数据库** | 原生节点+边 | Cypher 图遍历 | Neo4j / Graphiti |
| **关系型 DB** | 两张表：nodes 表 + edges 表 | SQL JOIN（多表连接模拟图遍历） | 很多企业知识图谱 |
| **内存** | 对象引用 + 邻接表 | 代码遍历 | 小规模图谱 |
| **文件** | JSON / RDF / Turtle | 加载后遍历 | 离线知识图谱导出 |
| **向量 DB** | 每个节点存一个 embedding | 向量相似（不做关系推理） | 不是真正的图谱查询 |

### 具体例子：用 MySQL 存知识图谱

```sql
-- 节点表
CREATE TABLE kg_node (
  id      VARCHAR PRIMARY KEY,
  type    VARCHAR,         -- User / Food / Category
  props   JSON             -- 其他属性
);

-- 边表
CREATE TABLE kg_edge (
  from_id VARCHAR,          -- 起点
  to_id   VARCHAR,          -- 终点
  type    VARCHAR,         -- RELATIVE_OF / ALLERGIC_TO / BELONGS_TO
  props   JSON             -- 边的属性（at / by / runId）
);

-- 查"用户亲属的过敏史"：SQL 多表 JOIN 模拟图遍历
SELECT f.props->>'$.content'
FROM kg_edge e1                                    -- 用户-亲属
JOIN kg_edge e2 ON e1.to_id = e2.from_id           -- 亲属-事实
JOIN kg_node f ON e2.to_id = f.id                  -- 事实内容
WHERE e1.from_id = 'userA'
  AND e1.type = 'RELATIVE_OF'
  AND e2.type = 'SAID'
  AND f.props->>'$.content' LIKE '%过敏%';
```

这**是**知识图谱（节点+边组织数据），但**不是**图数据库（存在 MySQL 里）。查询用 SQL JOIN 模拟图遍历，能跑，但深度遍历（3 跳以上）性能差--这是图数据库存在的理由。

---

## 4. 什么时候必须用图数据库

知识图谱存在 MySQL 里能跑，但**图遍历深度变深时性能急剧下降**：

```text
1 跳：用户 -> 他说过的事实           -> 1 次 JOIN，毫秒级
2 跳：用户 -> 亲属 -> 亲属说过的事实   -> 2 次 JOIN，毫秒级
3 跳：用户 -> 亲属 -> 亲属的同事 -> 同事说过的事实 -> 3 次 JOIN，开始慢
5 跳以上：多表 JOIN 爆炸，MySQL 扛不住   -> 这时候需要图数据库
```

图数据库用**邻接表索引**，图遍历不随深度爆炸：

```text
Neo4j 查 5 跳：O(分支因子^深度)，但索引优化后实测毫秒级
MySQL 查 5 跳：5 次 JOIN，O(表大小^5)，爆炸
```

所以：**浅度遍历的知识图谱不需要图数据库（关系型 DB 够），深度遍历的才需要。**

---

## 5. 回到 Agent Memory 场景

| 场景 | 要不要知识图谱 | 要不要图数据库 |
|------|-------------|---------------|
| 存"用户对花生过敏" | 不需要（一条条目够） | 不需要 |
| 存"用户说过 X，后来改口说 Y" | 不需要（supersede 链够） | 不需要 |
| 查"用户亲属的过敏史" | 需要（跨实体关联） | 看遍历深度，浅的话关系 DB 也行 |
| 查"这个 PR 沉寂 3 天了，关联 CI 失败 + 负责人请假" | 需要（多跳推理） | 大概率需要 |
| 查"3 个月前这条事实当时对不对" | 需要（时序） | Zep/Graphiti 用图做双时间轴 |

---

## 6. 总结

```text
知识图谱     = "用图组织数据"的形态选择（维度 1）
图数据库     = "专门存图、查图"的存储介质（维度 2）

知识图谱 ≠ 图数据库
知识图谱可以存在：图 DB / 关系 DB / 内存 / 文件
图数据库专门存：知识图谱（节点+边）

选不选用知识图谱：看你要不要"关系推理"
选不选用图数据库：看遍历深度，浅的用关系 DB 够，深的才需要图 DB
```

别人说"知识图谱"时要分清他讲的是**数据组织方式**还是**存储介质**--前者是设计决策，后者是工程选型。
