# 《agent4j 架构立场》骨架

> 用途：把"继承来的路线图"变成"自己的判断"。每个决策填五个字段，缺一不可。
> 填不出来的字段 = 你的缺口。填完回传逐条评审。

## 填法规则

每个决策必须填五个字段：

```
我的选择     → 一句话，明确立场，不许写"视情况而定"
对比替代     → 至少说一个"我没选"的方案，和它的相对优劣
代价         → 这个选择的成本，且要说清"谁来付"（用户/开发者/运行时/延迟/复杂度）
什么场景会改 → 一个具体的反例或触发条件，证明你不是盲信
证据         → agent4j 里哪个类/模块体现了这个选择
```

**自测标准**：

- 「代价」如果只写"会慢一点""有点复杂"——不合格。要具体到：谁慢、慢多少量级、哪个环节复杂。
- 「什么场景会改」如果写不出来——说明这不是你的判断，是继承来的路线图。
- 「对比替代」如果说不出另一个方案——说明你没做过真正的取舍。

## 校准样例（决策 0 已填，作为深度标准）

### 决策 0：Loop 是函数，不是线程

**我的选择**：`AgentLoop.execute(config, state) -> state`，纯函数式，不持有线程、不持有服务生命周期。

**对比替代**：把 Agent 做成一个常驻服务对象（内部维护消息队列 + 状态机 + 后台循环），像多数 LangChain 封装那样。

**代价**：所有历史必须塞在 `AgentState` 里作为参数传递——长任务会 token 膨胀；并发安全、背压、取消这些"服务级"问题全部推给调用方，框架不帮你管。

**什么场景会改**：如果要做「多用户共享一个 agent 实例、事件驱动、后台自动继续」的长驻服务（比如频道接力），纯函数 Loop 不够，得在它外面包一层常驻运行时 + 调度器——但我不会改 Loop 本身，而是在上层加。

**证据**：`ReActAgentLoop` + `SimpleAgent` 的委托结构；`notes/` 里"Loop 是函数，不是线程"的明确表述。

## 填空后的自检

1. 数一下「代价」字段有几个是具体的（能说出谁付、什么量级）。少于 15 个 → 判断力还停在"我知道为什么好"，没到"我知道好在哪、也贵在哪"。
2. 找出所有写不出「什么场景会改」的决策。那些就是继承来的设计，不是拥有的设计。这些决策在面试里被追问必挂。
3. 特别检查决策 17、21、22——这三条是"主动说不要"的。如果填的时候发现"我也说不清为什么不要，好像只是 v1 先不做"，说明边界感还是文档替你写的。
