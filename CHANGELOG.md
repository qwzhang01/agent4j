All record extensions keep japicmp binary compatibility with the 0.1.3 baseline through the tail-insert + legacy-constructor discipline. (1) Run identity columns: `RunRecord` tail-inserts `tenantId` + `versions` (immutable identity — written once at `DurableRunManager.createRow`, carried through every transition by row-copy, never rewritten; an agentId in RunContext writes the head entry `{"kind":"AGENT","name":"<agentId>","version":"unversioned"}`), `JdbcRunStore` DDL/INSERT/SELECT/fromRow carry both columns end to end, `InMemoryRunStore`/`DistributedRunControl` row-copies carry them, and `ComponentVersion.Kind` grows `AGENT` (no exhaustive switch existed — verified safe). The standard postmortem join "yesterday's bad batch, which tenant / which agent-model-prompt combination served it" is now answerable from the row, not reconstructed from logs. (2) Visit metadata: `StepRecord` tail-inserts `visitOrdinal`/`startedAt`/`endedAt` (+ legacy 5-arg constructor keeps visit fields null — honest absence), visit-aware factories for success/failed/paused/cancelled, `WorkflowState.record` assigns the 1-based ordinal at append (a recovered trace keeps its ORIGINAL ordinals — renumbering recovered history would falsify it), `GraphRuntime` main loop and `ParallelNode` branches record the `nodeStart..now` execution window. (3) Queue backpressure: `JdbcTaskQueue` gains a `(ConnectionSupplier, int capacity)` constructor — the guard meters non-terminal occupancy (PENDING+RUNNING) and refuses at capacity with `QueueFullException` (the same `[QUEUE_FULL]` signal family as `AsyncTaskQueue`), with `capacity()`/`totalRejected()`/`activeCount()` observability accessors; the DDL gains `tenant_id`, `enqueue` gains a 5-arg tenant-tagged signature (4-arg legacy delegates null), `TaskRow` carries tenantId through claim/complete/cancel row-copies, `listByTenant` isolates one tenant's in-flight rows. Honest boundary: the guard is an enqueue-time check, not a concurrency-safe quota — concurrent enqueues can briefly exceed capacity (same waterline as `AsyncTaskQueue`). (4) Tenant-ledger escalation budget: `SandboxSpec` gains `tenantId` (independent of runId — the tenant is the billing boundary), `SandboxEscalator.tryAcquireBudget(tenantId, runId)` is a two-tier claim — tenant ledger first (shared across the tenant's runs, so a noisy tenant cannot dilute other tenants even when each of its runs has budget left), then the per-run ledger, then the instance fallback; `getEscalationsUsedByTenant`/`getTrackedTenantCount` observability accessors. Note on the optimistic path: `SandboxPolicy.useOptimisticEscalation` stays `SEMI_TRUSTED && !multiTenant` — tenancy attribution rides on `SandboxSpec.tenantId`, not on the escalator's multiTenant flag (which routes direct-to-strong-tier and never touches the budget ledger). - **Stage 8.1: distributed execution - JDBC persistence spine, cross-instance control plane, partition tolerance (standard-harness roadmap).** The runtime graduates from "single JVM with in-memory bookkeeping" to "two instances, one database, safe takeover". The whole JDBC spine follows one dialect policy: plain ANSI SQL (H2 tests / PostgreSQL production), no MERGE, no ON CONFLICT, no FOR UPDATE SKIP LOCKED — every write is a guarded UPDATE whose affected-rows count IS the CAS verdict. Five JDBC backends in `agent-workflow/runtime/durable` (+1 in agent-core, +1 in agent-scheduler): `JdbcRunStore` (14-field RunRecord rows, optimistic version CAS, recovery-candidate sweep sorted by createdAt), `JdbcRunLeases` (single-winner INSERT-then-takeover-UPDATE, TTL expiry, holder-only renew/release, TTL=0 = never expires), `JdbcSideEffectLedger` (node-scoped and call-scoped idempotent effects, `DeliverySemantics`+`RetryDisposition` riding along), `JdbcCheckpointStore` (the missing shared blackboard — instance A's pause is instance B's resume; reuses `FileCheckpointStore.Snapshot` as the ONE codec for two transports, schema-version refusal identical whether the payload came from disk or a database), plus `JdbcApprovalStore` (agent-core) and `JdbcTaskQueue` (agent-scheduler, priority-DESC seq-ASC FIFO claim, `requeueOrphaned`). Every backend follows the CloseGuard connection discipline: supplier-backed stores release per operation, a shared single connection is borrowed but NEVER closed (the connection is fetched through `guard.get()`, never declared as a try-with-resources resource — the JVM's reverse-order auto-close would defeat the guard; this was found the hard way). New `DistributedRunControl` — the cross-instance control plane, built on one principle: THE RUN ROW IS THE CONTROL CHANNEL. Cancel from any instance is a row CAS to CANCELLED (only while still a recovery candidate; three outcomes CANCELLED/ALREADY_TERMINAL/NO_ROW, with a bounded 3-retry on version races); the owning instance observes the row through its heartbeat loop (upgraded from pure lease renewal to renew + row watch: a cross-instance cancel reaches the in-flight run within one poll period, ~250ms at the 500ms test TTL) and stops at a node boundary; a resume against a terminal row is refused loudly (`refusing to revive from a stale checkpoint` — checkpoints lag rows by design, rows are written at every transition, checkpoints only on pause). Approval callback across instances: decisions land in the shared approval store (idempotent derived approvalId keeps both instances on the same row); a late APPROVED on a cancelled run is on record but must not read as a green light — `approvalStillRelevant` guards it. `DurableRunManager` wires the control plane in: `assertResumable` after lease acquisition (lease AND row eligibility must both hold before any node executes), heartbeat row-watch fail-open on store hiccups (a control-channel blip must not kill a healthy run we still own — fail-open on intent, fail-closed on ownership), a `cancel(runId, reason)` facade (local live-run flag first, then the durable row), and a configurable `leaseTtlMs` (5-arg constructor; the hardcoded 60s TTL/20s heartbeat period was untestable). `RunLeases` is now an interface (`RunLeaseRegistry` the in-memory reference impl) so JDBC/Redis backends can slot in. `FileCheckpointStore.validateRunId` widened to public (the same runId whitelist guards SQL-bound ids). Partition tolerance (roadmap 8.1 "network partition, worker crash, database briefly unavailable"): `PartitionToleranceTest` uses H2 SHUTDOWN as the outage — every store operation against a dead database fails LOUDLY (IllegalStateException naming the operation; a silent "row updated" during a partition is the split-brain the CAS design exists to prevent), lease acquire during outage throws rather than silently granting, worker crash leaves recoverable state behind (row intact, next sweep lists it, B claims the lease and finishes), and the reconnect contract is stated honestly (H2 in-memory SHUTDOWN drops the schema — a deployment that must survive restarts uses a persistent DB; the test asserts, not assumes). The four-layer defense-in-depth is now complete: L1 spotlighting (new), L2 tool output as untrusted input (Stage 9 sanitizer, existing), L3 pre-request sanitization of everything the delegate returns (new — covers retrieved memories, not just tool output), L4 scoped identity (`IdentityConstrainedPermissionChecker`, existing). Honest boundaries: v1 is regex patterns, semantic detection (LLM judge) is the v2 interface slot; spotlighting is framing, not a guarantee — defenses stack, none is absolute; no real-LLM red-team run (Simon Willison-style cases belong to the Moonlit golden set). New tests: `SanitizingContextBuilderTest` (10: TOOL sanitization, clean passthrough, user-not-rewritten-only-framed, notice + wrapping, transient-SYSTEM not wrapped, spotlighting off, state keeps original bytes, byte-stable across calls, toolCalls survive rebuild, null/blank content passthrough). agent-security 59/59 (49 existing + 10 new). See [experiment notes](notes/experiment-kp10-indirect-injection.md).

## [0.1.2] - 2026-09-11

### Added

- **HTTP A2A, both directions (KP6).** agent4j is now a protocol citizen, not just a data-model tourist: `HttpA2AClient` speaks the A2A JSON-RPC dialect over real HTTP — `message/send` for task delegation, `tasks/get` for status polling, `GET /.well-known/agent.json` for discovery — and `HttpA2AServer` wraps an existing `Agent` as a protocol endpoint (JDK `HttpServer`, zero new dependencies; the agent itself is untouched, only how it answers the phone changes). The wire codec `A2AJson` is shared by both sides: where our model is richer than the spec (`taskType`/`sender`/`deadline`), the fields ride `params.metadata` so a spec peer that ignores metadata still round-trips what it understands; where the spec is richer than v1 (non-text parts), parsing skips instead of rejecting. Model alignment: `A2ATask` gains spec `contextId`/`status`/`artifacts` fields and `AgentCard` gains `url`/`capabilities`, with legacy 6-arg/5-arg constructors keeping all 170 existing construction sites compiling and behaving unchanged; task status is now the spec dialect (`working`/`completed`/`failed`/`input-required`/`canceled`/`rejected`, `A2ATaskStatus` enum) instead of free strings — `getTaskStatus` returns the enum, null for unknown tasks. Identity physics: the SERVER assigns task ids on the wire, so the HTTP client keeps a local-to-remote id map per instance. Defense on both sides of the wire: the server takes an optional inbound sanitizer (`UnaryOperator<String>`, a throwing sanitizer rejects the task as `rejected` BEFORE the agent runs — the a2a sibling of ExternalAgentWorker's outbound D5); the caller keeps wiring Stage 9's `ResultSanitizer` outbound as before. Honest v1 boundaries: synchronous execution only (no `message/stream` SSE, no push notifications), in-memory task store (lost on restart), no task continuation (a `message/send` carrying `message.taskId` is refused with `-32001`, loudly, not silently re-run), `sendMessage` refuses loudly over HTTP (the spec subset has no fire-and-forget method — faking it would silently CREATE a task), binds `127.0.0.1` only. New tests: `HttpA2ARoundTripTest` (real loopback sockets, zero mocks: full round-trip, discovery, failure, transport failure, restart-loses-store, inbound reject without running the agent, metadata rides the wire) and `HttpA2AServerProtocolTest` (raw-JSON protocol level: `-32601` unknown method, `-32700` parse error, `-32600` notification refusal, `-32001` continuation refusal / task-not-found, `-32602` non-text parts, HTTP verb rules, spec-dialect task shape). New example: `HttpA2AExample` (loopback demo: discover → send → poll → reject → supervisor routing over HTTP). agent-mcp 76/76 (59 existing + 17 new); agent-orchestrator 45/45 unchanged; full repo 22 modules BUILD SUCCESS.

### Added

- **PostgreSQL ledger (memory roadmap step 4).** The account book is now a database: `PgMemoryStore` is plain JDBC over a host-supplied `DataSource` (no pool, no ORM, no framework-owned migrations) with an idempotent schema of one 16-column ledger table, a `(scope, created_at DESC)` access index, and the step-4 centrepiece — a partial unique index `UNIQUE (scope, subject) WHERE status = 'ACTIVE'` that turns the reconciliation invariant "one ACTIVE line per subject" into a physical constraint: a racing second ACTIVE write surfaces as a unique violation instead of silently drifting into two. The `MemoryStore` port gains a default `supersede(closedOld, newEntry)` — sequential update-then-write in the default, overridden by `PgMemoryStore` as ONE transaction: a failure midway (e.g. the unique index rejecting the replacement after a racing writer won the slot) rolls the close back, so the ledger never ends with zero ACTIVE lines for a subject. All four supersede call sites (extract pipeline, `save_memory` tool, admin `approve`, admin `supersede`) now ride the atomic verb, and `EmbeddingMemoryStore` overrides it too so the decorator cannot silently decompose a persistent delegate's transaction. `write()` upserts on id (`INSERT ... ON CONFLICT (id) DO UPDATE`), the SQL shape of the in-memory map put — which lets approve activate a pending row in place inside the same transaction. Embeddings are stored as JSON float arrays in a text column, not pgvector: ranking happens in Java (`HybridRankingStrategy`), an ANN index buys nothing today, and a schema-pinned dimension would break embedding-model swaps; the upgrade path (`ALTER TABLE ... ADD COLUMN vector(dim)` + backfill + ANN index) never changes the ledger. Timestamps bind as `TIMESTAMPTZ` via `OffsetDateTime` UTC; enums bind as `name()` with strict `valueOf` read-back so a renamed enum value on old rows surfaces loudly. New abstract `MemoryStoreContractTest` turns the port's javadoc promises (scope isolation, ACTIVE-only default view, lazy TTL, exact filters, due windows, newest-first, upsert-on-id, the supersede move, full round-trips) into 19 machine assertions run against every implementation — `InMemoryMemoryStore` on every build, `PgMemoryStore` against a real zonky embedded PostgreSQL when `AGENT4J_PG_TEST=true`, including the two guarantees only a database can give: the partial index rejecting a second same-subject ACTIVE write (the first survives), and a mid-move unique violation rolling the close back (the racing writer's stamps survive, ours do not land). agent-memory 174/174 (134 existing + 40 new); PG line 21/21; full repo 22 modules serial BUILD SUCCESS. See [memory design discussion](notes/discussion-memory-system-design.md).

- **Layered memory injection (memory roadmap step 3, Letta core/archival alignment).** One recall, two tiers with different physics. The new `MemoryLayering` policy record (core importance threshold, default 0.9 + memory token budget, chars/4 heuristic) splits the recalled pool: core-tier entries (importance ≥ threshold) are the always-on working set, injected at the head as `[Core memories]` every turn, never ranked by the query and never dropped by the budget — stable head content keeps the prompt's longest-common-prefix long (E3 / decision 26 applied to memory). Archival-tier entries are paged in beside the last USER message as `[Known memories]`, re-ranked by relevance to that message — the same anchor the write-side reconciler uses, now defined once in `ConversationAnchors` so read and write can never drift — and trimmed by the remaining token budget. Placement physics: query-drifting content at the tail, identity content at the head. Recall is soft-failing: a broken recall degrades the turn's injection to "no memories", never breaks the chat loop. The 7-arg `MemoryContextBuilder` constructor opts in; the 6-arg constructor keeps the legacy single-block behaviour bit-for-bit, so all channel / tavern / enterprise call sites compile and behave unchanged. Flagship test: home-city (0.95) sits in core for every query while diet (0.7) and a keyboard purchase (0.65) trade places in archival depending on whether the user asks about lunch or keyboards. agent-memory 134/134 (129 existing + 5 new); full repo 22 modules serial BUILD SUCCESS, 2930 tests 0 failures. See [memory design discussion](notes/discussion-memory-system-design.md).

- **Reconciliation loop + bi-temporal timestamps (memory roadmap step 2).** The extract pipeline no longer extracts blind: `MemoryReconciler` recalls up to 20 ACTIVE old entries for the scope (read side feeds the write side) and renders them as an "Existing subjects" block in the extractor prompt, so the model picks an existing subject key instead of inventing a drifting one, and judges EVOLVE/CONFLICT against what the old entries actually say. `MemoryEntry` gains three bi-temporal fields — `validFrom` / `validAt` (business axis: when the fact was true in the world) and `invalidAt` (system axis: when the ledger closed the line) — with four backward-compatible constructors keeping all existing sites compiling unchanged. On supersede, the old entry is closed on both axes via `closedAs`: business axis at the NEW fact's business start (`validFrom`, falling back to `createdAt` — the user moved last week, not this Monday), system axis at now, so "when did I move" answers with the business date and old/new intervals never overlap. New `MemoryDecision` record captures every write decision (operation ADD/UPDATE/REJECT, subject, lifecycle, oldEntryId/newEntryId, recalled evidence, approvedBy, decidedAt/appliedAt) and is reported through the `MemoryDecisionListener` hook — the audit chain "who changed my memory and why". All three supersede sites (extract pipeline, `save_memory` tool, admin `approve`) follow one ledger rule. Soft failure throughout: a recall failure degrades to plain extraction, a broken listener never breaks the write. Flagship test: seed "home-city: lives in Shenzhen", feed "I moved to Shanghai" with `validFrom` = last week, assert Shenzhen becomes HISTORICAL with `validAt` = the business date (not recording time), Shanghai is the only ACTIVE entry, default recall sees Shanghai only, history query recovers Shenzhen, and one UPDATE decision is reported with both entry ids. See [memory design discussion](notes/discussion-memory-system-design.md).

- **Read-side semantic retrieval (memory roadmap step 1).** New `EmbeddingClient` port (`agent-core`) with `embed` / batch `embedAll` and a static `cosineSimilarity` that treats null/empty/mismatched vectors as "no signal" (0.0), plus `OpenAiEmbeddingClient` (`agent-model`) speaking the OpenAI-compatible `POST /embeddings` wire format (batch inputs, provider-side index re-ordering, same HTTP-status→ErrorCode mapping as `OpenAiModelClient`). `MemoryEntry` gains a 13th field `embedding` and an `embedText()` canonical text; three backward-compatible constructors keep all 56 existing construction sites compiling unchanged. New `EmbeddingMemoryStore` decorator (`agent-memory`) vectorizes entries on write with soft-failure semantics: an embedding outage logs a warn and writes the entry without a vector — read quality degrades, correctness never does; pre-vectorized re-writes pass through without re-billing. `HybridRankingStrategy` graduates from A8 stub to production (`score = 0.5·cosineSim + 0.3·tokenOverlap + 0.2·importance`) with a three-step degradation chain. Flagship test scenario: asking "relocation plans" surfaces `home-city: lives in Shenzhen` with zero lexical overlap. See [memory design discussion](notes/discussion-memory-system-design.md).

- **Prefix-cache visibility and a deterministic KV-cache simulator (E3, decision 26).** `CacheSimulatingModelClient` decorates any `ModelClient` and simulates prompt-cache prefix matching per model id: longest-common-prefix accounting against the previous prompt in the same domain, rough tokenization, hit/miss stats, and provider-reported `cachedTokens` wins when the vendor already reports hits. `CachePricing` prices a prompt in three mutually exclusive segments (`cached×read + written×write + base×input`, integer micro-USD) with `anthropic(...)` (read 0.1x, write 1.25x) and `openAiStyle(...)` (read 0.5x, writes free) factories. The `E3CacheExperimentTest` harness runs baseline / rewrite-flapping / rewrite-stable / tail-only / cascade scenarios under both pricing styles, each with a no-cache parallel line. Findings: compaction's volume reduction beats the cache loss it causes (even a flapping rewrite is cheaper than an untouched baseline); a frozen summary preserves ~24% more cache value than per-turn regeneration under Anthropic pricing; the ranking flips under OpenAI-style free-write pricing, so prefix discipline is vendor-priced, not a universal truth. See [experiment notes](notes/experiment-e3-prompt-caching.md), the [architecture walkthrough](notes/experiment-e3-architecture-walkthrough.md), and [decision 26](notes/architecture-stance-decision-26-cache-visibility-and-prefix-stability.md).

### Changed

The compact constructor clamps it (`< 0 → 0`, `> promptTokens → truncated`), and a 3-arg compatibility constructor defaults to 0 so existing construction sites compile unchanged. Wired through `CascadeModelClient`, `ModelCallMetrics` (7→8 params, compat constructor), `MetricsCollector` run totals, `RecordingSession` aggregation, and `TrajectoryCodec` JSON (`cached_tokens`; old archives read back as 0).

The clause is deliberately weak because cache hits are a runtime, post-hoc fact: a violation is not a compile error but a billing event, and `cachedTokens` visibility is the enforcement mechanism. ### Fixed
